# RangeQueryResearch

Исследовательский проект на C++23 для сравнения реализаций динамического множества с поддержкой порядковой статистики.

## Сборка

```sh
cmake --preset debug
cmake --build --preset debug
ctest --preset debug
```

Доступны пресеты `debug` для разработки, `release` для бенчмарков и
`sanitizers` для проверки AddressSanitizer и UndefinedBehaviorSanitizer. Все они используют Ninja и
создают изолированные каталоги `build/<preset>`.

```sh
cmake --preset sanitizers
cmake --build --preset sanitizers
ctest --preset sanitizers
```

Проект требует CMake 3.28 или новее и компилятор с поддержкой сканирования зависимостей C++ modules. Текущая конфигурация проверена с GCC 16 и CMake 4.4. Для runner используется Google Benchmark 1.9.4: CMake ищет установленный пакет этой версии, а при его отсутствии скачивает архив с проверкой SHA-256. Для автономной сборки можно передать `-DFETCHCONTENT_SOURCE_DIR_BENCHMARK=/path/to/benchmark-1.9.4`. Аналогично подключается header-only CLI11 2.7.2: сначала установленный пакет точной версии, затем архив с проверкой SHA-256; автономный источник задаётся через `-DFETCHCONTENT_SOURCE_DIR_CLI11=/path/to/CLI11-2.7.2`.

Исполняемый файл поддерживает `vector`, `set`, `avl` и `treap`. Для воспроизводимости экспериментов `treap` использует SplitMix64 с фиксированным seed. Все структуры хранят состояние непосредственно в приватных полях без pimpl; копирование создаёт независимое множество, перемещение оставляет пустой пригодный к использованию источник.

Оба исполняемых файла используют CLI11 для разбора аргументов, help и диагностики. `rangequery` по умолчанию выбирает `vector`; например, `rangequery --structure=avl`. В `rangequery_benchmark` обязательны `--structure` и `--mode` (`queries`, `insert`, `dynamic`); `--setup-count` должен быть положительным и указывается только для dynamic. `-h` или `--help` выводит библиотечную справку и завершает программу с кодом 0 без обработки stdin. Ошибки аргументов выводятся в stderr с кодом 2. Повторные одиночные параметры отклоняются; поведение help в сочетании с ошибочными аргументами определяется CLI11.

Модуль `rangequery.config` предоставляет настройки основного приложения (`Settings` и `read_command_line`) и общие CLI-помощники для выбора структуры. Настройки runner находятся отдельно в `rangequery.benchmark.config`: `BenchmarkMode`, `BenchmarkSettings` и `read_benchmark_command_line`. Обе функции разбора возвращают `std::expected`; при раннем завершении `unexpected` содержит код 0 или 2, а help или диагностика уже напечатаны библиотекой.

Удаление pimpl изменяет размещение объектов и стоимость операций. Для сравнения производительности нужны отдельные новые прогоны; исторические CSV сохраняются как результаты прежней реализации.

## Бенчмарки

Для асимптотических графиков используется размер множества `data_size`, а не длина потока команд. Отдельный C++ runner заранее читает и разбирает весь workload. В query-сценариях он также строит множество до запуска таймера и измеряет только `q`, `m` и `n`; в insert-сценариях измеряются все `k`. В dynamic-сценариях начальные вставки выполняются вне таймера, после чего целиком измеряется фаза с чередованием вставок и запросов.

Основная метрика — wall time операций структуры, измеренный Google Benchmark (`UseRealTime`); process CPU time (`MeasureProcessCPUTime`) записывается как дополнительная диагностика. Parsing, setup query-сценария, запуск и завершение процесса, обмен через stdin/stdout, проверка результата и форматирование JSON в измерение не входят. Аллокации внутри самой операции структуры входят. Одна итерация Google Benchmark — один полный проход измеряемой части workload (`Iterations(1)`, `Repetitions(1)`); независимые повторы и порядок структур задаёт Python. Setup выполняется до benchmark-цикла, а validation и уничтожение структуры — после него. Результаты запросов сохраняются наблюдаемыми через `benchmark::DoNotOptimize`, изменения структуры — через escape указателя на неё и `benchmark::ClobberMemory` в конце прохода.

```sh
python3 tools/benchmark.py \
  --runner build/release/src/rangequery_benchmark \
  --output benchmark-results/scaling.csv \
  --data-sizes 1000 10000 100000 \
  --query-count 1000 \
  --query-kind rank \
  --density sparse \
  --build-config Release
```

Для проверки локальности обращений используются одинаковые множества среднего размера и большое количество запросов; `hotspot` концентрирует их вокруг центральных 5 % ключей.

```sh
python3 tools/benchmark.py \
  --runner build/release/src/rangequery_benchmark \
  --output benchmark-results/locality.csv \
  --data-sizes 1000 3000 10000 \
  --query-count 100000 \
  --query-kind rank \
  --localities uniform hotspot \
  --build-config Release
```

CSV schema version 4 отдельно хранит `setup_operation_count`, `measured_operation_count`, полное `command_count`, начальный и конечный размеры, фактический workload seed и количества операций каждого вида. Основная величина для графиков — `wall_ns_per_operation`; `cpu_ns_per_operation` предназначена для диагностики. Поля `measurement_scope=structure_operations`, `wall_clock=google_benchmark` и `cpu_clock=process` фиксируют методику измерения. Поля `benchmark_engine`, `benchmark_version` и `benchmark_iterations=1` идентифицируют измерительный движок. `compiler`, `compiler_version` и `build_config` сообщает runner из конфигурации CMake; `--build-config` задаёт дополнительную метку `build_label`. Встроенный reporter сохраняет прежние поля JSON и возвращает суммарное время всего прохода в наносекундах. Исторические CSV schema version 3 можно анализировать отдельно, но не следует смешивать с version 4 в одном сравнении; новые численные результаты требуют повторного запуска матрицы.

После каждого измерения runner вне таймера возвращает стабильный FNV-1a checksum. В query-сценарии он хеширует ответы запросов; в insert-сценарии — размер и пробы итогового множества. Для dynamic-потока runner заново проигрывает операции на чистой структуре, хеширует каждый ответ в состоянии на момент запроса и добавляет пробы итогового множества из измеренной структуры. Python вычисляет ожидаемое значение по тому же протоколу до запуска и не записывает CSV, если checksum или число измеренных операций не совпали. Эта sanity-проверка защищает результаты эксперимента, но не заменяет полные контрактные тесты.

Основной практический эксперимент использует начальные размеры 1 000, 10 000 и 100 000 и точные доли успешных вставок 1 %, 10 %, 50 % и 90 %. Остальные операции поровну распределены между `q`, `m` и `n`. Для каждой точки создаются пять независимых потоков с seed 42–46, каждый измеряется трижды; порядок структур между повторами перемешивается детерминированно.

```sh
python3 tools/benchmark.py \
  --runner build/release/src/rangequery_benchmark \
  --output benchmark-results/dynamic.csv \
  --scenario dynamic \
  --seeds 42 43 44 45 46 \
  --repetitions 3 \
  --build-config Release
```

Полные графики, таблица лидеров и исследовательский вывод находятся в `notebooks/benchmark_results.ipynb`.

Сохранённые численные результаты для `treap` являются историческими: они получены до перехода генератора приоритетов со `std::mt19937_64` на SplitMix64. Для численного сравнения с текущей реализацией benchmark-матрицу необходимо запустить заново; приведённые ниже выводы относятся к старому прогону.

На зафиксированной машине `ordered_vector` лидирует при 1–50 % вставок для 1 000 начальных ключей, при 1–10 % для 10 000 и только при 1 % для 100 000. При большей доле вставок лидирует AVL; он также является наиболее устойчивым выбором при неизвестной заранее динамической смеси. Treap в этой матрице не победил, а `std::set` существенно проиграл из-за линейных `rank` и `select`. Это результат конкретного Release-прогона со sparse-uniform нагрузкой, а не универсальная граница для всех распределений.

Сценарий `regimes` сравнивает структуры не по заранее выбранной «лучшей» операции, а по диапазонам размера и плотности. Внутри каждого режима все четыре структуры получают один и тот же входной поток.

| Режим | Размеры | Ключи | Нагрузка |
| --- | --- | --- | --- |
| `small_dense_rank` | 1 000–10 000 | плотные, из непрерывного диапазона | 10 000 запросов ранга |
| `medium_dense_rank` | 10 000–100 000 | плотные | 1 000 запросов ранга |
| `medium_sparse_rank` | 10 000–100 000 | разреженные, по широкому диапазону `int` | 1 000 запросов ранга |
| `medium_sparse_mixed` | 10 000–100 000 | разреженные | поровну `rank`, `select` и запросы интервала |
| `large_sparse_random_growth` | 10 000–100 000 | разреженные | вставки в случайном порядке |
| `large_sparse_ascending_growth` | 10 000–100 000 | разреженные | вставки в возрастающем порядке |
| `large_sparse_descending_growth` | 10 000–100 000 | разреженные | вставки в убывающем порядке |

Пара плотных и разреженных режимов проверяет, влияет ли расположение ключей в их числовом диапазоне. Три режима роста отделяют стоимость структуры от порядка поступления данных: возрастающий поток благоприятен для отсортированного вектора, убывающий требует сдвигать элементы, а случайный ближе к реальному потоку. Плотность и порядок сохраняются в CSV, поэтому результаты нельзя случайно смешать.

```sh
python3 tools/benchmark.py \
  --runner build/release/src/rangequery_benchmark \
  --output benchmark-results/regimes.csv \
  --scenario regimes \
  --build-config Release
```
